# Written-layer conformance format, v0

The TypeScript and Python low levels (the config as written: documents, statements, values, copies, variables,
resolutions, edits and save) must produce these files byte for byte from the same input. The rules they implement
are in `spec/spec.md` sections 6 and 7.3 (first written in `.claude/design/consumer-api/round12/slices.md`
section 2 and `design.md`; where the two differ, the spec wins and the difference is reported). The expected outputs
here were derived by hand from those rules, not generated by either implementation; a runner that disagrees with
one has found a bug in itself or in the rules, never a reason to rewrite the file.

The case files spell operations and error groups with fixed tokens (`set`, `BadTextError`). They are data,
not names a binding must use: each runner maps them to its own spelling of the spec names with the table under
"Tokens" below.

## Inputs

`conformance/written/cases.json`: a JSON array of cases, each

```
{"name", "needs", "files"? | "fixture"?, "root", "overrides"?, "extensions"?, "steps"}
```

- `name`: unique; the expected output is `conformance/written/expected/<name>.json`.
- `needs`: what the case uses. A runner skips a case needing a token it does not implement yet; a finished runner
  implements every token and skips nothing.
  - `include` (the include extension), `snippet` (`snippet` and `use` lines);
  - `values`: `set` on a `set line` and on a `variable`, a value's `replace with text`;
  - `statements`: a statement's `replace with text` and `remove`;
  - `save`, `quote`;
  - `directive-values`: `set` on a `written directive` and on a `use line`, a value's `remove`;
  - `blocks`: `insert statements`, `add statements`, and a statement's `insert before` and `insert after`;
  - `rename`: `rename` on a `written directive` and on a `variable`;
  - `document`: a document's `replace with text`;
  - `override`: the graph's `set override`.
- `files`: path to text, served with the runner's `memory source` (spec 4.3). Or `fixture`: a directory
  under `fixtures/` whose `*.conf` files are served the same way, by path relative to it.
- `root`: the path loaded. `overrides`: the load's `overrides` option, by name without `$`.
- `extensions`: absent (none) or `["include"]`. There is no key rule: rendered addresses are positional.
- `steps`: run in order on the one graph the case loads; each gives one entry of the output.

## Expected output

A JSON array with one entry per step. Places are `path:line:col` (0-based line, UTF-16 column, the span's start).
Every position is in UTF-16 units, whatever unit the binding reports (`spec/contract.md` 1): a runner whose binding
counts code points or bytes converts each position with the text it counts in (the document's text, or for a `bad
text error`, the text the edit was given).
A **copy text** is the load-conformance origin text (`conformance/load/format.md`) of `{place, via}`: for a
statement's copy, `place` is the statement's `place`; for a reference's resolution, the reference's `place` with
the resolution's `copy.via`. A **variable text** is its `place`, `override <name>` for an override, or `null`.

### Steps

- `["list"]`:
  `{"files": [[path, [edge, ...]], ...], "edges": [[copy, [spec, ...], [target, ...]], ...],
  "variables": [[name, kind, place | "override", [win, ...], [[shadowed at, winner], ...]], ...],
  "diagnostics": [[code, origin], ...]}`. `files`: each document (documents order) and its `included by ()` edges
  as their copy texts. `edges`: `graph.edges()`. `variables`: `graph.variables()`; each `wins ()` and `shadowed at
  ()` resolution as its copy text, a `shadowed at ()` one with its winner's variable text. `diagnostics`: the
  graph's `diagnostics`.
- `["references"]`: every reference of every document (documents order, then text order, list items and slice
  bounds included) as `[place, declaration, [[copy, winner, [shadowed, ...]], ...]]`: its declaration's variable
  text, then each of its `resolutions ()` with `winner` and `shadowed` as variable texts.
- `["render"]`: the load-conformance object of `render (graph)` without `files` (`directives`, `unreadable`,
  `diagnostics`), each argument extended to `[text, origin, definition, [[reference, winner], ...]]`:
  `definition` its place or `null`; each step of its `chain` as the reference's copy text and the winner's
  variable text. (Before milestone 1 this field was the rendered value's `written`, which meant the end of the
  chain; the expected files did not change.)
- `["texts"]`: each document whose `text` differs from its `saved text`, as `[path, text]`, documents order.
- `["save"]`: the graph's `save (writer)` with a recording writer: what the writer got, `[[path, text], ...]` in
  batch order; `[]` when it was not called.
- `["edit", target, op, ...args]`: the op on the target. An op exists only on the types where it can succeed (spec
  6.5, 6.7), so no case calls one where it is absent (milestone 2 removed `override-no-set-line`, which called `set`
  on an override variable). Output `["ok"]`, `["ok", [text, ...]]` for an op that
  returns handles (their `text`s), or `["error", name, [[code, line, col], ...]]` with the edit error's token
  (below) and a `bad text error`'s diagnostics, located in the text given (spec 2.8; `[]` for the others).
- `["quote", text]`: `quote(text)`.

### Targets

- `["document", path]`; `["graph"]`.
- `["statement", path, line, col]`: the statement whose name token (the first token of its `place` that is not a
  comment, space or line break) starts there.
- `["block", path]`: the document's `block`; `["block", path, line, col]`: that statement's block.
- `["value", path, line, col]`: the written value starting there (list items and slice bounds included; a
  reference at its `$`).
- `["variable", path, line, col]`: the variable whose `$name` starts there; `["override", name]`: the override
  variable of that name.
- `["rendered", address, arg, step, "winner" | "reference"]`: render now; the directive at that people address,
  `values[arg].chain[step]`, then its `winner` or `reference`.
- `["previous"]`: the target of the previous `edit` step (as it was resolved then: the same handle).
- `["returned"]`: the first handle the most recent edit that returned handles returned.

### Tokens

| Token in the case files | Spec name (spec.md) |
|---|---|
| op `"set"`, with `text` | `set` |
| op `"replaceWithText"`, with `text` | `replace with text` |
| op `"remove"` | `remove` |
| op `"rename"`, with `name` | `rename` |
| op `"insertStatements"`, with `index`, `text` | `insert statements` |
| op `"addStatements"`, with `text` | `add statements` |
| op `"insertBefore"`, with `text` | `insert before` (a statement) |
| op `"insertAfter"`, with `text` | `insert after` (a statement) |
| op `"setOverride"`, with `name`, `text` or `null` | `set override` (`null` is absent) |
| error `"BadTextError"` | `bad text error` |
| error `"DetachedError"` | `detached error` |

> **Proposed (pending owner):** spell these tokens with the spec names (`"set override"`, `"bad text error"`) so no
> runner reads TypeScript names. It changes every case file and runner, so it waits for the owner with the rest of
> the conformance proposals (spec 9).
>
> **Proposed (pending owner):** a copy text uses the statement's `place`, which starts at an owned comment, while
> targets and rendered directive origins use the name token. A commented extension line would print its copy on
> the comment's line. The proposal: anchor copy texts at the name token too. No case has such a line yet, so no
> expected file would change; both runners would.

## Bytes

As `conformance/format.md`: no insignificant whitespace, every character above U+007F escaped as lowercase
`\uXXXX` UTF-16 code units, one trailing `"\n"`.
