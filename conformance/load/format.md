# Load conformance format, v0

Every binding's load and render must give these files byte for byte from the same input, through the shared driver
([spec/conformance.md](../../spec/conformance.md)) (R17: the same
codes, places, trees, addresses and change lists). The rules they implement are in `spec/spec.md`
sections 2, 4.3, 5, 6.2 and 7 (first written in `.claude/design/consumer-api/round11/slices.md` §1; where the two
differ, the spec wins and the difference is reported). The expected outputs here were derived by hand from those
rules, not generated by either implementation; an output that disagrees with one has found a bug in the binding or
in the rules, never a reason to rewrite the file.

## Inputs

`conformance/load/cases.json`: a JSON array of cases, each

```
{"name", "needs", "files", "root", "overrides"?, "key"?, "extensions"?, "after"?}
```

- `name`: unique; the expected output is `conformance/load/expected/<name>.json`.
- `needs`: a subset of `["snippet", "include", "diff", "key"]`: what the case uses beyond `set` and `$name`, as a
  record. The driver reads only `include` from it, for the case's level (L3).
- `files`: path to text. The driver sends them in `load`; the adapter serves them with its binding's `memory
  source` (spec 4.3), loads the graph, and the driver asks for `render(load(root))`.
- `root`: the path loaded.
- `overrides`: the load's `overrides` option, by name without `$`.
- `key`: absent (no key rule) or the name of a key rule in `conformance/keys.json` (`"rasl"`, below): the driver
  sends the rule's data in `render` and `diff`, and the adapter builds its binding's key rule from it
  ([spec/conformance.md 4.3](../../spec/conformance.md#43-key-rules-as-data)).
- `extensions`: absent (none) or `["include"]` (the include extension).
- `after`: path to replacement text for a second load and render (other files unchanged; since milestone 3 the
  driver loads it as a second `load` with the merged files, so by a second processor: spec 7.1 lets `diff` compare
  any two renders);
  the expected output's `changes` are `first.diff(second)` of the two renders (spelled as the binding spells a
  render's `diff (after, key?)`).

The `"rasl"` key rule, as data in `conformance/keys.json`: a `node` directive whose parent is `graph` is keyed by its
second argument's text; `connect` by its arguments' texts joined by one space; `fill` by its first argument's text;
everything else has no key.

## Expected output

One JSON object of the first render, with exactly these keys in this order:

```
{"files":[path,...],
 "directives":[[address, block, origin, [[text, origin],...]],...],
 "unreadable":[[containerAddress, reason, origin],...],
 "diagnostics":[[code, origin],...],
 "changes":[[kind, address],...]}
```

- `files`: the graph's document paths in first-read order.
- `directives`: every directive in walk order (depth-first, written order). `address` is the people form
  (`graph > node "leds" > max_count`); `block` is whether it was written with a block; then the directive's
  origin; then each argument's canonical text and origin.
- `unreadable`: the top level's unreadable statements first (`containerAddress` `""`), then each directive's, the
  directives taken in walk order; within one container, in the order they stand. `reason` is the unreadable's
  `reason` (spec 2.4, 7.2).
- `diagnostics`: the render's diagnostics in order, each origin built from its `place` and `via`; a warning's entry
  ends with `"warning"` (conformance/format.md, "Severity"). `load-include-glob-empty` holds only a warning: the
  load and the render go on (spec 2.3).
- `changes`: present only when the case has `after`: `[kind, address]` per change, in `diff`'s order.

An origin is one string: its place as `path:line:col` (0-based line, UTF-16 column, the span's start), or
`override <name>` for a value from an override; then for each `via` step, innermost first,
` < <kind> <name> <path>:<line>:<col>` (kind `variable`, `use` or `extension`). Example:
`main.conf:4:21 < variable source main.conf:2:10 < use twinkle main.conf:4:9`.

## Bytes

As `conformance/format.md`: no insignificant whitespace, every character above U+007F escaped as lowercase
`\uXXXX` UTF-16 code units, one trailing `"\n"`.
